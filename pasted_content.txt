Bonjour à tous,

Je souhaite clarifier un point d'architecture qui n'est pas encore dans le Guide d'Intégration mais qui sera important lors de l'intégration centralisée.

Le contexte : actuellement vous développez vos modules en standalone et vous appelez /api/users/me depuis vos propres services pour valider le contexte utilisateur. C'est le bon pattern pour votre phase de développement actuelle.

L'évolution prévue : lors de l'intégration centralisée, ce sera le backend BankMatch qui appellera directement vos microservices. Dans ce cas, vos modules n'auront plus besoin de valider le JWT utilisateur ni d'appeler /api/users/me. Le backend BankMatch validera le JWT et transmettra le contexte utilisateur via un token interne.

Le déroulement complet sera le suivant.

1. L'utilisateur s'authentifie et obtient un JWT.
2. L'utilisateur appelle une API BankMatch avec son JWT.
3. BankMatch valide le JWT et extrait le contexte utilisateur.
4. BankMatch génère un token interne valable 30 secondes contenant tenantId, userId et roles.
5. BankMatch appelle votre microservice avec ce token interne.
6. Votre microservice valide le token interne, pas le JWT utilisateur.
7. Votre microservice traite la requête avec le contexte fourni.

Pourquoi ce choix.

Le microservice n'a jamais besoin du secret JWT utilisateur, les secrets restent séparés. Si un microservice est compromis, l'impact reste limité à ce seul service. Le token interne est très court, ce qui limite fortement les risques de rejeu. Les tokens internes peuvent aussi être tracés séparément pour l'audit.

Ce que vous pouvez préparer dès maintenant.

Ajoutez une variable d'environnement dans votre module, par exemple INTERNAL_SERVICE_SECRET, avec une valeur temporaire comme internal_dev_secret pour l'instant.

Créez une fonction de validation de token interne dans votre FastAPI, par exemple :

import jwt
import os
from fastapi import Header, HTTPException

INTERNAL_SERVICE_SECRET = os.getenv("INTERNAL_SERVICE_SECRET", "internal_dev_secret")

def verify_internal_token(authorization: str = Header(...)):
    if not authorization.startswith("Bearer "):
        raise HTTPException(status_code=401, detail="Missing bearer token")
    token = authorization.split(" ", 1)[1]
    try:
        payload = jwt.decode(token, INTERNAL_SERVICE_SECRET, algorithms=["HS256"])
    except jwt.ExpiredSignatureError:
        raise HTTPException(status_code=401, detail="Internal token expired")
    except jwt.InvalidTokenError:
        raise HTTPException(status_code=401, detail="Invalid internal token")
    if payload.get("type") != "internal":
        raise HTTPException(status_code=401, detail="Wrong token type")
    if not payload.get("tenantId"):
        raise HTTPException(status_code=401, detail="Missing tenantId")
    return payloadUtilisez cette fonction comme dépendance sur vos endpoints, par exemple :

@router.post("/analyze")
def analyze(payload: dict, ctx: dict = Depends(verify_internal_token)):
    tenant_id = ctx["tenantId"]

Pendant votre développement, vous pouvez continuer à fonctionner sans le backend BankMatch, soit en gardant un endpoint de démo séparé qui n'utilise pas cette validation, soit en ajoutant un flag qui désactive la validation en développement, soit en générant un token interne localement avec un petit script.

Point important : votre module doit continuer à fonctionner en développement sans le backend BankMatch. La validation du token interne sera réellement activée lors de l'intégration centralisée.

Quand ce pattern sera réellement utilisé.

Pour mon propre module IA, dès que je connecterai mon AI Service au backend BankMatch, ce qui arrivera bientôt. Pour vos modules, au moment de l'intégration centralisée. Fraud Detection sera probablement le premier module concerné vu son avancement.
