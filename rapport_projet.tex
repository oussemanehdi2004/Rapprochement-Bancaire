\chapter{Introduction}
\section{Contexte du stage}
Le stage que j'ai effectué dans le cadre de ma formation s'est déroulé dans une entreprise spécialisée dans le développement de solutions numériques pour le secteur financier. Il a été l'occasion pour moi de découvrir de près le fonctionnement d'un projet informatique réel, avec ses contraintes, ses difficultés et ses objectifs de production.

Le secteur bancaire évolue rapidement et les entreprises ont besoin d'outils fiables pour gérer leurs flux financiers, contrôler leurs opérations et détecter les anomalies. Les transactions bancaires sont de plus en plus nombreuses, parfois complexes, et leur analyse manuelle devient difficile et coûteuse. C'est dans ce contexte que le projet de rapprochement bancaire prend toute sa valeur.

Le rapprochement bancaire consiste à comparer les mouvements financiers enregistrés dans les comptes avec les données internes de l'entreprise afin de repérer les écarts, les erreurs et les transactions suspectes. Il aide à améliorer la fiabilité des données financières et à sécuriser les opérations.

\section{Présentation du projet}
Le projet sur lequel j'ai travaillé s'appelle \textbf{Rapprochement Bancaire}. Son objectif principal est de développer une plateforme capable d'importer des fichiers bancaires, de normaliser les transactions, de vérifier la cohérence des données et d'analyser le risque de fraude.

Le système est conçu autour de plusieurs modules complémentaires. Le premier s'occupe de l'ingestion des fichiers bancaires dans différents formats. Le second transforme ces données en un format unique pour faciliter leur traitement. Le troisième vérifie la qualité des données. Le quatrième analyse les transactions pour détecter les anomalies et les signaux suspects. Enfin, l'interface permet de visualiser les résultats et de suivre l'évolution du système.

Ce projet est intéressant car il combine plusieurs aspects du développement informatique : traitement des données, conception d'API, intégration de services, sécurité, intelligence artificielle et gestion de projet.

\section{Objectifs du stage}
Les objectifs de mon stage étaient les suivants :
\begin{itemize}[leftmargin=1.5em]
    \item comprendre l'architecture globale du système ;
    \item participer au développement de modules clés du projet ;
    \item traiter des fichiers bancaires dans plusieurs formats ;
    \item normaliser et valider les transactions ;
    \item intégrer les différents services du projet ;
    \item tester les fonctionnalités et détecter les points à améliorer ;
    \item rédiger un rapport clair sur le travail réalisé.
\end{itemize}

Ce stage a été l'occasion d'acquérir de nouvelles compétences techniques et de mieux comprendre le travail en équipe, la gestion des tâches et les contraintes d'un projet réel.

\chapter{Présentation générale du projet}
\section{Le contexte fonctionnel}
Aujourd'hui, les entreprises gèrent un très grand nombre de transactions bancaires. Les mouvements peuvent venir de plusieurs banques, selon plusieurs formats et plusieurs canaux de transmission. La gestion manuelle de ces données est souvent source d'erreurs, de retard et de mauvaise qualité d'information.

Dans ce contexte, une solution de rapprochement bancaire doit permettre de :
\begin{itemize}[leftmargin=1.5em]
    \item importer les relevés bancaires ;
    \item standardiser les informations ;
    \item identifier les transactions en doublon ;
    \item comparer les mouvements bancaires et les données comptables ;
    \item détecter les opérations anormales ou frauduleuses ;
    \item générer des rapports utiles pour la décision.
\end{itemize}

Le projet répond donc à un besoin concret et très important dans le secteur financier.

\section{Architecture générale du système}
Le système développé est organisé de manière modulaire. Il regroupe plusieurs services qui travaillent ensemble pour traiter les données bancaires.

On trouve notamment :
\begin{itemize}[leftmargin=1.5em]
    \item un service d'ingestion pour charger les fichiers bancaires ;
    \item un service de parsing pour lire les fichiers et extraire les transactions ;
    \item un module de validation pour vérifier les informations ;
    \item un service de détection de fraude pour analyser les transactions ;
    \item une interface utilisateur pour visualiser les résultats ;
    \item des outils de monitoring et de suivi du système.
\end{itemize}

Cette architecture est utile car elle permet de séparer les responsabilités. Chaque module a un rôle précis, ce qui rend le système plus facile à comprendre, à tester et à maintenir.

\section{Les modules du projet}
Le projet comprend plusieurs modules. Parmi les plus importants, on retrouve :
\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Multi-Banking} : module de chargement et de normalisation des fichiers bancaires ;
    \item \textbf{Fraud Detection} : module d'analyse des transactions pour détecter les risques ;
    \item \textbf{Frontend} : interface pour gérer les imports et afficher les résultats ;
    \item \textbf{Monitoring} : outils de supervision et de suivi des services ;
    \item \textbf{Intégration API} : échanges entre les services via des requêtes HTTP et des tokens sécurisés.
\end{itemize}

Les autres modules développés par mes collègues complètent le projet et participent à une vision globale de la plateforme. Même si mon travail a principalement porté sur la partie ingestion et analyse, j'ai aussi eu conscience de l'importance des composants autour de la sécurité, de l'intégration et de la supervision.

\chapter{Module Multi-Banking}
\section{Rôle du module}
Le module Multi-Banking est l'un des éléments centraux du projet. Son rôle est d'importer les fichiers bancaires et de les transformer dans un format exploitable par le système.

Sans cette étape, les transactions ne seraient pas structurées, et l'analyse de fraude ne pourrait pas être faite correctement. C'est donc la base du projet.

\section{Formats supportés}
Le système doit accepter plusieurs types de fichiers bancaires, car les banques n'utilisent pas toujours le même format. Les formats que nous avons pris en charge incluent :
\begin{itemize}[leftmargin=1.5em]
    \item CSV ;
    \item CAMT.053 ;
    \item MT940 ;
    \item autres formats standards bancaires selon le besoin du projet.
\end{itemize}

La prise en charge de plusieurs formats est essentielle dans un contexte bancaire réel. Elle permet au système d'être plus robuste et d'évoluer plus facilement selon les partenaires ou les banques concernées.

\section{Normalisation des données}
Une fois les fichiers lus, il faut transformer les informations pour les rendre homogènes. C'est ce qu'on appelle la normalisation. Les transactions sont converties vers un format pivot unique, avec des éléments comme :
\begin{itemize}[leftmargin=1.5em]
    \item la référence de la transaction ;
    \item la date de valeur ;
    \item le montant ;
    \item le libellé ;
    \item le compte source ;
    \item le compte bénéficiaire ;
    \item l'IBAN ;
    \item le tenant ou l'identifiant de l'utilisateur.
\end{itemize}

Cette étape est très importante, car elle permet d'uniformiser les données avant qu'elles ne soient analysées.

\section{Validation des transactions}
Avant de passer à l'étape suivante, le système vérifie la qualité des données. Cela consiste à contrôler plusieurs éléments :
\begin{itemize}[leftmargin=1.5em]
    \item validité des montants ;
    \item cohérence des dates ;
    \item présence des champs clés ;
    \item intégrité des comptes ;
    \item vérification des doublons ;
    \item contrôle des IBAN et des informations bancaires.
\end{itemize}

Cette validation réduit les erreurs et évite que des données incomplètes ou incohérentes soient transmises au module suivant.

\section{Travail réalisé sur ce module}
Pendant le stage, j'ai participé à la logique d'import, de parsing et de validation. J'ai aussi contribué à la préparation des données pour que le service de détection de fraude puisse les utiliser sans ambiguïté.

Cette partie du projet est très importante, car la qualité de l'analyse dépend directement de la qualité des données d'entrée.

\chapter{Module Fraud Detection}
\section{Rôle du module}
Le module Fraud Detection est le cœur de la logique métier du projet. Il reçoit les transactions traitées par le module Multi-Banking et analyse leur niveau de risque.

L'objectif est de détecter les opérations inhabituelles, les schémas suspects et les comportements qui peuvent indiquer une fraude.

\section{Approche hybride}
Le système ne se base pas sur une seule méthode. Il combine plusieurs approches :
\begin{itemize}[leftmargin=1.5em]
    \item règles métier ;
    \item analyse statistique ;
    \item modèles de machine learning ;
    \item analyse de graphes.
\end{itemize}

Cette approche est utile car certains cas peuvent être détectés simplement par des règles, tandis que d'autres exigent une analyse plus avancée.

\section{Règles métier}
Les règles métier servent à repérer rapidement les situations inhabituelles. Parmi les exemples, on peut citer :
\begin{itemize}[leftmargin=1.5em]
    \item montant supérieur à un seuil fixé ;
    \item retrait cash anormal ;
    \item transactions répétées à haute fréquence ;
    \item présence de mots-clés sensibles dans le libellé ;
    \item changement de bénéficiaire ou de compte inhabituel ;
    \item variation anormale du solde.
\end{itemize}

Ces règles permettent de lancer une première alerte rapide sur les transactions suspectes.

\section{Modèle de machine learning}
En plus des règles métier, le système utilise des modèles de machine learning pour estimer le risque associé à une transaction. Les données analysées peuvent inclure le montant, le type de transaction, le compte source, le compte destinataire et l'historique des mouvements.

Le résultat est généralement un score ou une probabilité qui permet de classer les transactions selon leur niveau de suspicion.

\section{Analyse de graphes}
Le système inclut aussi la détection de relations entre comptes et transactions. Cette étape est utile pour repérer des schémas plus complexes, comme des flux circulaires, des associations suspects entre comptes ou des mouvements répétitifs entre plusieurs comptes.

Cette analyse est intéressante car elle permet d'identifier des comportements frauduleux qui ne sont pas visibles en regardant une transaction isolée.

\section{Travail réalisé}
J'ai participé à l'analyse de ce module, à la compréhension du flux de données entre les services et à la validation du comportement global du système. J'ai également contribué à l'intégration du service avec les autres composants du projet.

Le point important ici est que la qualité du module de détection de fraude dépend directement de la qualité des données qu'il reçoit. C'est pour cette raison que les étapes d'ingestion et de validation sont si importantes.

\chapter{Autres modules et intégration du projet}
\section{Interface utilisateur}
Le frontend du projet est une interface qui permet de charger les fichiers, de visualiser les transactions et d'afficher les résultats d'analyse. Il s'agit d'un élément important, car il rend le système utilisable par des utilisateurs non techniques.

Grâce à cette interface, les données peuvent être suivies de manière plus simple. Les analystes et les responsables peuvent consulter les alertes, les scores de risque et les indicateurs de performance.

\section{Monitoring et supervision}
Le projet intègre aussi des outils de supervision pour vérifier que les services fonctionnent correctement. Cela comprend notamment le suivi des API, l'état des services et les éventuelles erreurs de fonctionnement.

Le monitoring est essentiel dans un environnement technique, car il permet de détecter rapidement un problème avant qu'il n'impacte l'utilisation du système.

\section{Sécurité et authentification}
La sécurité est un élément crucial dans un projet bancaire. Les échanges entre services doivent être sécurisés et les données sensibles doivent être protégées. C'est pourquoi le projet met en place des mécanismes d'authentification interne, tels que les tokens JWT, pour contrôler les accès entre composants.

Même si cette partie ne constitue pas le cœur métier de mon travail, elle est indispensable pour garantir la fiabilité du système.

\section{Intégration des services}
Un projet de cette taille ne fonctionne pas si les services sont isolés. Il faut qu'ils communiquent correctement entre eux via des API et des formats de données cohérents.

Dans notre cas, le système s'appuie sur plusieurs services qui doivent échanger des informations dans un ordre précis :
\begin{enumerate}[leftmargin=1.8em]
    \item import des fichiers ;
    \item lecture et transformation des transactions ;
    \item validation des données ;
    \item transmission au module de détection de fraude ;
    \item affichage des résultats et suivi de l'analyse.
\end{enumerate}

Cette chaîne de traitement montre bien la logique globale du projet.
