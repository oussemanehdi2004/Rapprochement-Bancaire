\section{Contexte du stage}

J'ai effectué mon stage au sein de l'entreprise ELITECOM du 7 juillet au 7 septembre 2026. L'entreprise développe des solutions numériques pour le secteur financier, notamment des plateformes SaaS d'intelligence financière. Mon stage s'est concentré sur le développement de deux modules clés d'une plateforme de rapprochement bancaire : Multi-Banking et Fraud Detection.

Le contexte du stage était technique : j'ai travaillé sur du code Python (FastAPI) pour le backend, avec des tests en pytest, et j'ai manipulé des fichiers bancaires de test dans différents formats (CSV, CAMT.053, MT940). Pendant ces deux mois, j'ai dû construire un pipeline fiable pour traiter les transactions bancaires et détecter les anomalies, en m'intégrant à un codebase existant plutôt qu'en partant d'un projet vide.

\section{Présentation du projet}

Le projet s'inscrit dans un contexte plus large de gestion financière intelligente et de détection des anomalies sur les mouvements bancaires. Mon périmètre a porté sur les services d'ingestion et de normalisation bancaire, ainsi que sur leur intégration avec le moteur de détection de fraude. J'ai dû comprendre l'architecture existante pour situer mon travail et éviter de casser les fonctionnalités déjà en place.

    \item \textbf{Étudié} : analyse/compréhension sans développement principal ;

Le système repose sur deux modules principaux :

\section{Problématique}

Les entreprises reçoivent des relevés bancaires dans des formats hétérogènes (CSV, CAMT.053, MT940) avec des structures différentes. Par exemple, un fichier CSV peut avoir des colonnes comme \texttt{account\_iban}, \texttt{value\_date}, \texttt{label}, \texttt{amount}, tandis qu'un fichier CAMT.053 XML organise les données dans une structure hiérarchique avec des balises comme \texttt{<Ntry>}, \texttt{<Amt>}, \texttt{<CdtDbtInd>}. Ces différences rendent le traitement automatisé difficile.

La problématique technique que j'ai rencontrée est : comment normaliser ces formats disparates vers un schéma pivot unique, valider les transactions (IBAN, dates, montants, doublons avec tolérance ±0.02 EUR), et les transmettre au moteur de fraude via API REST avec authentification JWT ?

\section{Objectifs du stage}

Les objectifs du stage étaient à la fois techniques et méthodologiques. Ils se déclinaient comme suit :

\begin{itemize}
    \item développer et stabiliser les parsers CSV, CAMT.053 et MT940 dans \path{multi-banking/parsers/} ;
    \item mettre en place un schéma pivot de transactions et valider les données avant leur transmission ;
    \item implémenter la détection de doublons avec une tolérance explicite pour gérer les écarts de représentation des montants ;
    \item sécuriser les échanges inter-services via JWT interne et gérer les cas d'erreur avec retry ;
    \item valider le pipeline complet par des tests d'intégration ciblés et documenter les limites fonctionnelles ;
    \item corriger le bug de regex dans le parser MT940 qui faisait perdre le premier chiffre du montant.
\end{itemize}

L'objectif n'était pas de construire l'ensemble d'une plateforme SaaS complète, mais de rendre fiable le flux d'ingestion et de normalisation bancaire et de le connecter au module de détection de fraude existant. En pratique, cela signifiait comprendre un code existant, modifier des fonctions sans casser les autres services, et m'assurer que les données transmises respectaient le format attendu par le moteur de fraude.

\section{Présentation de l'entreprise}

ELITECOM intervient dans le développement de solutions numériques destinées à accompagner les transformations du secteur financier et de la gestion d'entreprise. L'entreprise place l'innovation technologique au service des besoins liés à la gestion financière, à la sécurité des transactions et à l'exploitation des données.

Dans ce contexte, la mise en place d'un système de rapprochement bancaire et de détection de fraude répond à un besoin réel : réduire le travail manuel, sécuriser les opérations et améliorer la qualité des décisions basées sur les données financières.

\section{Analyse des besoins fonctionnels}

Le système doit traiter des fichiers bancaires dans des formats hétérogènes. Par exemple, dans le module Multi-Banking, j'ai dû développer des parsers pour :

\begin{itemize}
    \item \textbf{CSV} : lecture avec \texttt{csv.DictReader}, extraction des colonnes \texttt{account\_iban}, \texttt{value\_date}, \texttt{label}, \texttt{amount}, \texttt{counterparty\_iban}, \texttt{reference} ;
    \item \textbf{CAMT.053} : parsing XML avec \texttt{lxml.etree}, extraction des balises \texttt{<Ntry>}, \texttt{<Amt>}, \texttt{<CdtDbtInd>}, \texttt{<ValDt>}, \texttt{<AddtlNtryInf>} ;
    \item \textbf{MT940} : parsing avec regex, extraction des lignes \texttt{:61:} (transactions) et \texttt{:60F:} (solde).
\end{itemize}

Après parsing, les transactions sont normalisées vers le modèle \texttt{PivotTransaction} avec les champs : \texttt{tenant\_id}, \texttt{bank\_id}, \texttt{account\_iban}, \texttt{value\_date}, \texttt{label}, \texttt{amount}, \texttt{currency}, \texttt{counterparty\_iban}, \texttt{reference}, \texttt{source\_format}, \texttt{source\_line\_hash} (SHA-256).

Les besoins fonctionnels sont :

\begin{itemize}
    \item ingérer des fichiers CSV, CAMT.053 et MT940 via l'endpoint \path{/banking/api/multi-banking/ingest} ;
    \item normaliser vers \texttt{PivotTransaction} avec hash SHA-256 pour déduplication ;
    \item valider : IBAN présent, date ISO 8601 valide, montant non nul, doublons détectés (tolérance ±0.02 EUR) ;
    \item transmettre au service Fraud Detection via \texttt{POST /api/analyze} avec authentification JWT ;
    \item recevoir les résultats d'analyse : score de risque, règles déclenchées, explicabilité SHAP.
\end{itemize}

\section{Besoins non fonctionnels}

\textbf{Sécurité} : Les services communiquent via JWT avec le secret partagé \path{FRAUD_INTERNAL_SECRET}. Dans \path{multi-banking/main.py}, j'ai implémenté la génération du jeton avec \texttt{jwt.encode()} et sa transmission dans l'en-tête HTTP \texttt{Authorization}, selon le schéma Bearer.

\textbf{Fiabilité} : Le système inclut un mécanisme de retry avec backoff exponentiel (3 tentatives, délai initial 0.5s) pour les appels au service Fraud Detection. Les erreurs sont loggées avec request ID UUID pour traçabilité.

\textbf{Testabilité} : J'ai écrit des tests d'intégration dans \texttt{test\_integration\_suite.py} couvrant le pipeline complet : parsing → validation → appel fraud service (mocké avec respx). Les tests vérifient les cas d'erreur (fichier vide, format invalide, service indisponible).

\section{Choix de conception}

\subsection{Float vs Decimal pour les montants}

Le type \texttt{float} a été utilisé pour faciliter l'intégration avec les bibliothèques ML. Cependant, il peut entraîner de légères erreurs d'arrondi.

Une tolérance de ±0,02 EUR est donc utilisée lors de la comparaison des montants. En production, l'utilisation de \texttt{Decimal} serait préférable pour garantir une meilleure précision monétaire.

\subsection{Algorithme JWT HS256}

L'algorithme HS256 a été choisi pour sécuriser les communications internes entre les services.

Il présente l'avantage d'être simple à mettre en œuvre et adapté à notre environnement de développement, avec un secret partagé entre les services.

Pour une architecture multi-tenant en production, une solution basée sur des clés asymétriques pourrait être envisagée afin de renforcer la séparation et la gestion des clés.

\subsection{Parsers maison vs bibliothèques existantes}

Des parsers personnalisés ont été développés pour CSV, CAMT.053 et MT940 afin de mieux contrôler la transformation des données vers notre schéma pivot.

Cette approche facilite également l'intégration de la déduplication par SHA-256 et l'ajout de traitements spécifiques aux besoins du projet.

Les bibliothèques existantes n'ont pas été retenues car elles offraient moins de flexibilité pour ces transformations.

\chapter{Module Multi-Banking}

\section{Rôle fonctionnel}

Le module \textbf{Multi-Banking} reçoit les fichiers bancaires, les lit selon leur format, extrait les transactions et les transforme en un format exploitable par le reste du système. C'est la première étape du pipeline et elle influence directement la qualité de l'analyse finale. Pendant le stage, j'ai dû comprendre comment différents formats bancaires représentent la même information (montant, date, IBAN) et comment les normaliser vers un schéma commun.

\section{Formats de fichiers bancaires et de paiement pris en charge}

Le module a été conçu pour traiter plusieurs types de fichiers. Cette capacité est particulièrement importante dans le paysage réel de la finance, où les banques n'utilisent pas tous le même standard de transmission.

Les formats pris en charge incluent notamment :
\begin{itemize}
    \item CSV ;
    \item CAMT.053 (ISO 20022) ;
    \item MT940 (SWIFT) ;
    \item PAIN.001 (ISO 20022) : le projet contient un parser PAIN.001 accompagné de tests unitaires. Toutefois, contrairement aux trois formats principaux de mon périmètre (CSV, CAMT.053 et MT940), son intégration complète dans le pipeline d'ingestion reste à considérer comme partiellement validée. Le parser est chargé dynamiquement et retourne une erreur si non disponible ;
    \item formats bancaires standardisés avec normalisation de données.
\end{itemize}

Ces différents formats peuvent présenter les mêmes informations de manière structurée différemment. Les libellés, les dates, les montants et les identifiants de compte n'ont pas toujours la même représentation. Le système doit donc normaliser ces différences pour produire un schéma unique.

La fonction \texttt{validate\_transactions()} dans \texttt{validators.py} implémente la validation :

\begin{itemize}
    \item \textbf{IBAN obligatoire} : vérifie que \texttt{account\_iban} n'est pas vide ;

La détection de doublons avec tolérance compare les montants et vérifie si l'écart est ≤ 0.02 EUR, ce qui gère les erreurs d'arrondi bancaire typiques.

Originale : r":61:(\d{6})(\d{4})?([CD])(\w)?([\d,]+)"
Corrigée  : r":61:(\d{6})(\d{4})?([CD])([A-Za-z])?([\d,]+)"
\end{verbatim}

\section{Machine Learning et explicabilité}

Le système de détection de fraude repose sur plusieurs composants ML. J’ai principalement étudié leur fonctionnement et leur intégration, tout en vérifiant que les données provenant de Multi-Banking respectaient le format attendu.


\subsection{Modèles et composants ML existants}

Le système utilise une approche hybride combinant plusieurs modèles de Machine Learning existants :

\noindent\textbf{Pipeline de chargement} : \path{main.py} charge prioritairement \path{model_fraud_calibrated.pkl} (XGBoost calibré) et utilise \path{model_fraud.pkl} comme solution de repli.

\noindent\textbf{Random Forest} : Ce modèle sert de référence pour le benchmark. Il repose sur \path{RandomForestClassifier} avec les paramètres \path{n_estimators=150}, \path{max_depth=8} et \path{class_weight="balanced"}. Une expérimentation de calibration a également été menée avec \path{CalibratedClassifierCV} sur des données synthétiques.

\noindent\textbf{XGBoost calibré} : Ce modèle prioritaire est stocké dans \path{model_fraud_calibrated.pkl}. Ses principaux paramètres sont \path{n_estimators=300}, \path{max_depth=6} et \path{learning_rate=0.1}. Une calibration isotone est appliquée et le seuil optimal est déterminé par maximisation du F1-score.

\noindent\textbf{Isolation Forest} : Algorithme de détection d'anomalies non supervisé, complémentaire aux modèles de classification supervisée.

\noindent\textbf{SHAP} : Technique d'explicabilité qui identifie les variables influençant le plus la décision du modèle (montant, comportement du compte, fréquence des transactions).

\noindent\textbf{Règles métier} : Le moteur de règles (\texttt{rules\_engine.py}) applique des règles déterministes basées sur des seuils et mots-clés (SEUIL\_REGLEMENTAIRE > 10\_000 EUR, MOTCLE\_SENSIBLE, FRACTIONNEMENT\_SUSPECT, etc.).

\subsection{Fusion des scores}

Pour obtenir un score de risque global, le système combine les scores issus des différentes sources de détection à l’aide de la fonction \texttt{fuse\_scores()}.
\begin{itemize}
    \item Score de base : probabilité ML (XGBoost calibré ou Random Forest) ;
    \item intégration d'Isolation Forest : ajout de 30\% du score d'anomalie, plafonné à 1 ;
    \item intégration des règles de lot : ajout de 20\% de la probabilité calculée sur le lot, plafonné à 1 ;
    \item fusion avec les règles métier : \(1-(1-\text{base})(1-\text{règle})\).
\end{itemize}

\subsection{Variables du modèle}

Les variables utilisées par les modèles sont définies dans \texttt{features.py} et comprennent 13 features principales :
\begin{itemize}
    \item \path{amount}, \path{oldbalanceOrg}, \path{newbalanceOrig}, \path{oldbalanceDest}, \path{newbalanceDest}
    \item \path{sender_balance_error}, \path{receiver_balance_error}
    \item \path{is_transfer}, \path{is_cash_out}
    \item \path{amount_to_avg_ratio}, \path{hour_of_day}, \path{days_since_last_tx}, \path{beneficiary_tx_count}
\end{itemize}

\subsection{Sources et données d'entraînement}

Les modèles utilisent différentes sources de données :
\begin{itemize}
    \item \textbf{Dataset PaySim} : Pour l'entraînement XGBoost calibré (jusqu'à 1 million de lignes)
    \item \textbf{Données synthétiques} : Pour l'entraînement Random Forest calibré (10 000 échantillons)
    \item \textbf{Données de test} : Fichiers \texttt{sample.csv} et \texttt{sample\_camt.xml} pour les tests
\end{itemize}

\textbf{Limites} : Les métriques précises d'entraînement (AUC-PR, précision, rappel) et les caractéristiques détaillées du jeu de données n'étaient pas toutes disponibles dans la documentation du projet.

\section{Sécurité des échanges}

L'authentification inter-services est implémentée avec JWT (détaillé dans le chapitre 3). Le secret partagé est défini dans \texttt{.env} : \texttt{FRAUD\_INTERNAL\_SECRET}. En développement, l'authentification peut être désactivée avec \texttt{DISABLE\_INTERNAL\_AUTH=true} (jamais en production).

\subsection{Limites et angles morts de sécurité}

\textbf{Isolation multi-tenant} : Le \texttt{tenant\_id} est actuellement fourni par le client puis intégré au JWT. Pour une véritable isolation multi-tenant, il devrait être vérifié par un service d'authentification central avant d'être utilisé.

\textbf{Gestion des secrets} : Les secrets utilisés actuellement sont principalement adaptés à l'environnement de développement. En production, ils devraient être remplacés par des secrets sécurisés et correctement gérés.

\textbf{Expiration des tokens} : L'expiration des JWT internes n'est pas encore configurée dans l'implémentation actuelle. Une durée limitée, comme 30 minutes, est prévue pour renforcer la sécurité.

\textbf{Parsing XML} : Le parsing des fichiers CAMT.053 avec \texttt{lxml} doit être sécurisé contre les attaques XXE. Une configuration sécurisée du parseur est recommandée.

\textbf{Choix de JWT} : HS256 a été retenu pour sa simplicité dans l'environnement actuel. Pour une architecture multi-tenant en production, l'utilisation de clés asymétriques pourrait offrir une meilleure gestion des clés.

\textbf{Logging de secrets} : Le code contient actuellement un logging de variables de configuration sensibles dans \path{multi-banking/main.py}  qui expose potentiellement le secret. Ce log doit être supprimé avant un déploiement de production.

\chapter{Difficultés rencontrées et apprentissages}

\section{Difficultés techniques}

\textbf{Bug du parser MT940} : Le groupe générique \verb|\w| de la regex originale acceptait les chiffres dans le "funds code" et faisait perdre le premier chiffre du montant. La correction restreint ce groupe aux lettres (détaillé dans le chapitre 4).

\textbf{Intégration JWT} : La configuration de l'authentification inter-services a nécessité de comprendre le flux Multi-Banking → Fraud Detection. J'ai dû configurer les variables d'environnement \texttt{FRAUD\_INTERNAL\_SECRET} et \texttt{DISABLE\_INTERNAL\_AUTH}, et implémenter la génération de token avec \texttt{jwt.encode()}. En développement, l'authentification peut être désactivée, mais j'ai appris que cela ne doit jamais être activé en production.

\textbf{Tolérance de doublons} : La détection de doublons avec tolérance ±0.02 EUR pour gérer les erreurs d'arrondi bancaire a été complexe à implémenter. J'ai dû comparer les montants avec une tolérance et vérifier le hash de base sans le montant pour détecter les transactions similaires.

\section{Difficultés organisationnelles}

Le projet impliquait plusieurs modules et plusieurs développeurs. J'ai dû comprendre l'architecture globale pour situer mon travail. Le document \path{ARCHITECTURE_DECISIONS.md} a facilité la compréhension des décisions d'architecture et de l'intégration avec BankMatch.

\section{Apprentissages personnels}

J'ai appris à développer des parsers pour des formats bancaires réels (CSV, CAMT.053, MT940), à implémenter des validations avec tolérances, à configurer l'authentification JWT entre services, et à écrire des tests d'intégration avec pytest et respx. J'ai aussi découvert l'importance de la qualité des données : une donnée mal validée peut fausser les résultats de fraude.

Avant le stage, je connaissais Python et FastAPI de manière théorique. Maintenant, je sais les utiliser dans un contexte réel avec authentification, retry exponentiel, logging structuré et monitoring Prometheus. Ce qui m'a particulièrement marqué, c'est la différence entre développer un projet à partir de zéro et intervenir sur un code existant : il faut comprendre les conventions déjà en place, ne pas casser les fonctionnalités des autres services, et documenter ses propres choix pour que les autres développeurs puissent comprendre le raisonnement.

\section{Bilan personnel}

En travaillant sur un système financier concret et en manipulant des fichiers bancaires de test représentatifs de situations rencontrées dans ce type de projet, j'ai développé des compétences techniques en parsing de fichiers, validation avec tolérances, authentification JWT, tests d'intégration et monitoring. J'ai aussi appris l'importance de la documentation technique et de la communication avec l'équipe.

\chapter{Bilan et perspectives}

\section{Bilan du travail réalisé}

Le travail effectué a permis de développer et de stabiliser le flux d'ingestion bancaire dans le module Multi-Banking, puis de le relier au moteur de détection de fraude. La contribution principale a porté sur les parseurs, la validation des transactions, la génération du token interne JWT et la vérification du pipeline d'intégration. Les parties liées à la détection de fraude et aux modèles ML ont été étudiées et intégrées dans le système existant, sans constituer l'ensemble d'une architecture de conception originale de ce moteur.

\section{Limites de mon intervention}

Il est important de préciser clairement les limites de mon intervention dans ce projet :

\begin{itemize}
    \item \textbf{BankMatch non activé} : L'intégration avec la plateforme BankMatch est implémentée dans le code mais désactivée par défaut (\path{BANKMATCH_INTEGRATION_ENABLED=false}) en attente de la finalisation du contrat API par l'équipe BankMatch.
    \item \textbf{Tests E2E non réalisés} : Les tests d'intégration utilisent des mocks (respx) pour simuler le service Fraud Detection. Un véritable test end-to-end avec les services réels n'a pas été réalisé.
    \item \textbf{Moteur ML existant} : Les modèles de Machine Learning (Random Forest, XGBoost, Isolation Forest, SHAP, Neo4j) étaient déjà présents dans le projet. Mon travail a consisté à les étudier et à intégrer les données dans ce moteur existant.
    \item \textbf{PAIN.001} : Le parser PAIN.001 a été développé et testé, mais son intégration complète dans le pipeline d'ingestion reste à valider.
\end{itemize}

\section{Limites actuelles du système}

Le système présente plusieurs limites techniques et fonctionnelles qu'il convient de signaler de manière honnête :

\subsection{Limites des données et modèles}

\begin{itemize}
    \item \textbf{Données synthétiques} : Les modèles ML ont été entraînés sur des données synthétiques (PaySim, données générées par \texttt{generate\_synthetic\_data()}). Ces données ne reflètent pas nécessairement les patterns de fraude réels et peuvent limiter la généralisation du modèle en production.
    \item \textbf{Métriques d'entraînement} : Les métriques précises d'entraînement (AUC-PR, précision, rappel, F1-score) n'étaient pas toutes disponibles dans la documentation du projet. Seul l'AUC-PR du XGBoost calibré est mentionné dans le script d'entraînement.
    \item \textbf{Dataset PaySim} : Le dataset PaySim est une simulation et ne capture pas la complexité des comportements de fraude réels. De plus, le script d'entraînement charge un sous-ensemble (1 million de lignes) du dataset complet.
    \item \textbf{Caractéristiques des données} : Les informations détaillées sur la distribution des variables, la corrélation entre features et les patterns de fraude spécifiques au contexte métier n'étaient pas documentées.
\end{itemize}

\subsection{Limites fonctionnelles}

\begin{itemize}
    \item \textbf{Couverture de tests} : Le retry exponentiel n'est pas couvert par les tests automatisés. Certains scénarios d'erreur (timeouts, erreurs réseau spécifiques) ne sont pas testés.
\end{itemize}

\subsection{Limites techniques}

\begin{itemize}
    \item \textbf{Représentation des montants} : La détection de doublons repose sur une tolérance explicite de ±0.02 EUR pour compenser l'utilisation de \texttt{float} au lieu de \texttt{Decimal}. Cette tolérance est fonctionnelle mais doit être configurable selon le contexte client.
    \item \textbf{Retry exponentiel} : Le retry exponentiel est codé en dur (3 tentatives, délai initial 0.5s). Il pourrait être externalisé dans la configuration si le service était déployé plus largement.
    \item \textbf{Secrets JWT} : Selon \texttt{TESTING\_FINDINGS\_AND\_RECOMMENDATIONS.md}, les secrets JWT actuels font 19-24 octets, en dessous des 32+ octets recommandés par la RFC 7518.
    \item \textbf{Parsing XML} : L'utilisation de \texttt{lxml} pour le parsing des fichiers CAMT.053 expose potentiellement à des attaques XXE (XML External Entity) si non configuré correctement.
\end{itemize}

\subsection{Limites de périmètre}

\begin{itemize}
    \item Le périmètre de la plateforme BankMatch et les détails de l'orchestration centrale ne sont pas entièrement couverts dans ce rapport.
    \item Les modules de trésorerie, de reporting et d'assistance financière (AI Financial Copilot) n'étaient pas dans mon périmètre technique.
    \item Le rapprochement bancaire proprement dit relève d'un périmètre plus large que celui de ce stage.
\end{itemize}


\section{Perspectives d'amélioration}

Les améliorations prioritaires concernent la validation complète du système dans des conditions proches de la production :

\begin{itemize}
    \item finaliser le contrat API de BankMatch et activer l'intégration correspondante ;
    \item réaliser des tests end-to-end avec les services réels exécutés via Docker Compose ;
    \item intégrer complètement le parser PAIN.001 dans le pipeline d'ingestion ;
    \item remplacer progressivement les montants en \texttt{float} par \texttt{Decimal} et rendre configurables la tolérance de déduplication ainsi que les paramètres de retry ;
    \item renforcer la gestion des secrets JWT et sécuriser le parseur XML contre les attaques XXE ;
    \item évaluer les modèles de fraude sur des données réelles anonymisées et documenter précisément leurs métriques de performance.
\end{itemize}

\chapter{Conclusion}

Au début de mon stage, la partie Multi-Banking n'était pas encore développée. J'ai donc pris en charge sa conception et son développement depuis le départ, en passant progressivement de l'analyse du besoin à la mise en place de l'architecture, du traitement des fichiers bancaires, des mécanismes de validation, de l'API, de la sécurité et des tests. Une grande partie de mon travail a ainsi consisté à construire un module capable de traiter les données bancaires de manière fiable et à l'intégrer progressivement dans l'écosystème de la plateforme.

En parallèle, la partie Fraud Detection disposait déjà de plusieurs modèles de Machine Learning lorsque j'ai commencé mon stage. Je n'ai donc pas cherché à recréer ces modèles, mais plutôt à comprendre leur fonctionnement et la manière dont ils étaient utilisés dans le projet. Mon travail a surtout porté sur leur exploitation et sur la connexion entre les données produites par le module Multi-Banking que j'ai développé et les composants de détection de fraude existants. Cela m'a également permis de mieux comprendre comment un modèle de Machine Learning s'intègre dans une application réelle, au-delà de son simple entraînement.

Cette distinction est importante pour présenter correctement ma contribution : j'ai développé le module Multi-Banking et les différents composants nécessaires à son fonctionnement, tandis que les modèles de détection de fraude constituaient un existant que j'ai étudié, exploité et intégré. Le stage m'a ainsi permis de travailler à la fois sur la construction complète d'un service backend et sur son intégration avec des composants de Machine Learning déjà disponibles.
